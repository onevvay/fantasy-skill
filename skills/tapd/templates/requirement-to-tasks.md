# TAPD 需求拆分为任务模板

这份模板用于把一个 TAPD 需求拆成可分派、可验收、可独立回填的任务。任务标题统一使用“工作类型 + 动作 + 交付对象 + 验收结果”的结构，避免出现“完成需求”“相关开发”等无法验收的标题。

## 一、任务标题规范

### 推荐格式

```text
【工作类型】动作 + 交付对象（关键范围或验收结果）
```

工作类型使用一个明确的主责领域，不要把多个领域合并在同一个标题中。推荐使用以下固定值：

| 工作类型 | 适用范围 |
| --- | --- |
| `前端` | 页面、组件、交互、前端状态和接口接入 |
| `后端` | 接口、领域逻辑、权限、数据处理和数据库变更 |
| `测试` | 测试用例、接口测试、回归测试、E2E 和验收证据 |
| `发布` | 构建、部署、配置、版本核验、回滚和发布后检查 |
| `产品` | 规则、流程、验收口径和业务配置 |
| `设计` | 视觉、交互、原型和设计交付物 |
| `数据` | 数据准备、修复、迁移、校验和报表 |
| `运维` | 监控、告警、网络、资源和运行保障 |
| `安全` | 权限、审计、敏感数据和安全验证 |
| `文档` | 用户文档、接口文档、发布说明和运维手册 |

如确有新的稳定工作类型，再补充到固定列表；不要随意创造同义标签。跨领域工作应拆成多个任务，例如分别创建 `【前端】...`、`【后端】...` 和 `【测试】...`，不要使用 `【前端/后端】`。

### 标题规则

1. `【工作类型】` 必须位于标题开头，且只能填写一个固定工作类型。
2. 工作类型后使用明确动作，例如“新增、实现、调整、修复、补充、联调、编写、验证、发布、配置、迁移”。
3. 标题必须写清交付对象和完成结果；建议控制在 50 个中文字符以内。
4. 一个标题只表达一个主要交付物。出现“并且”“同时完成多个模块”等情况时，优先拆成多个任务。
5. 需求 ID、TAPD 链接、版本号、分支和详细步骤放在任务字段或描述中，不用来替代交付对象和验收标准。
6. 不使用“完成需求、开发一下、测试一下、相关工作、配合处理、优化代码”等无法判断完成条件的表述。

### 标题示例

```text
【前端】实现订单详情状态展示（覆盖空态与权限态）
【后端】新增订单列表查询接口（支持分页与权限过滤）
【测试】补充订单状态流转回归用例（覆盖正常与异常路径）
【发布】发布订单状态变更至测试环境（完成版本核验与回滚点记录）
【数据】补齐历史订单状态映射（完成兼容性校验）
```

## 二、需求拆分清单模板

```markdown
### 需求信息

- 需求名称：
- TAPD 需求 ID：
- TAPD 链接：
- 所属迭代/版本：
- 需求背景：
- 业务目标：
- 全局验收口径：
- 明确不包含：
- 需求负责人：

### 任务清单

| 序号 | 任务标题 | 负责人 | 前置任务 | 交付物 | 验收状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | `【产品】明确{{业务规则}}验收口径` | {{姓名}} | 无 | {{规则/原型/验收口径}} | 未开始 |
| 2 | `【后端】实现{{接口或领域能力}}（{{关键边界}}）` | {{姓名}} | 1 | {{接口/逻辑/数据变更}} | 未开始 |
| 3 | `【前端】实现{{页面或交互}}（{{关键状态}}）` | {{姓名}} | 1、2 | {{页面/组件/交互}} | 未开始 |
| 4 | `【测试】验证{{功能}}（覆盖{{测试范围}}）` | {{姓名}} | 2、3 | {{用例/报告/截图证据}} | 未开始 |
| 5 | `【发布】发布{{功能}}至{{环境}}（完成{{核验项}}）` | {{姓名}} | 4 | {{版本/部署/回滚信息}} | 未开始 |
```

不需要产品或设计任务时删除对应行；不涉及发布时不要为了凑流程创建发布任务。任务数量以“每个任务都有独立负责人、交付物和验收标准”为准。

## 三、单个任务描述模板

将下列内容粘贴到 TAPD 任务描述中，并删除不适用字段：

```markdown
## 任务目标

{{用一句话说明本任务要交付什么，以及它如何支撑关联需求。}}

## 关联信息

- 关联需求：{{TAPD 需求 ID / 链接}}
- 所属迭代/版本：{{迭代或版本}}
- 负责人：{{姓名}}
- 前置任务：{{任务标题或任务 ID；无则填写“无”}}
- 协作方：{{姓名/角色；无则填写“无”}}

## 工作范围

### 包含

- {{本任务需要完成的内容}}

### 不包含

- {{明确排除的内容，避免与其他任务重复}}

## 前置条件

- {{依赖的接口、数据、设计稿、权限或环境}}

## 验收标准

1. {{可观察、可复核的完成条件}}
2. {{正常场景或主流程的结果}}
3. {{异常、空态、权限、兼容性或回滚边界；按需填写}}

## 交付物与证据

- 交付物：{{代码/接口/用例/部署版本/文档等}}
- 自测或测试结果：{{命令、用例、结果或报告链接}}
- 截图/附件证据：{{可访问链接或 TAPD 附件；无则填写“无”}}

## 风险与影响

- 功能影响：{{受影响功能；无则填写“无”}}
- 数据影响：{{数据修复、迁移或兼容性；无则填写“无”}}
- 发布影响：{{配置、依赖、回滚或环境要求；无则填写“无”}}

## 计划信息

- 预计工时：{{小时}}
- 计划完成时间：{{YYYY-MM-DD}}
- 分支/提交/版本：{{完成后回填}}
```

## 四、拆分完成检查

- 每个任务标题都符合 `【工作类型】动作 + 交付对象（关键范围或验收结果）`。
- 每个任务只有一个主要交付物，并且有明确负责人。
- 任务之间的前置关系已填写，没有依赖隐藏在描述或口头沟通中。
- 每个任务至少有一条可复核的验收标准，测试和发布任务写明环境、版本或证据要求。
- 需求的全局验收口径已经分解到前端、后端、测试和发布任务，且没有遗漏异常、权限、数据或回滚边界。
- 任务描述未把本地构建、提交或 CI 结果冒充真实业务 E2E 验收；涉及 UI 或用户操作时已预留可访问截图证据。
