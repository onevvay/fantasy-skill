# TAPD 全生命周期技能

通过官方 MCP Server（`mcp-server-tapd`）或 TAPD 开放 API（REST）管理需求、任务、缺陷、迭代、工时、评论、测试用例等。

## 一、MCP Server 安装与启用

### 1. 前置条件

```bash
brew install uv        # 或 curl -LsSf https://astral.sh/uv/install.sh | sh
which uvx              # 确认可用
```

### 2. 获取凭据（二选一，推荐 Token）

- **个人访问令牌（推荐）**：TAPD 网页 → 我的设置 → 个人访问令牌 → 创建。只显示一次，务必保存。
- **API 账号密码（兼容）**：公司管理 → API 账号管理，复制 API 账号（`TAPD_API_USER`）和密钥（`TAPD_API_PASSWORD`）。

### 3. 启用（按客户端配置）

**Kimi Code** — 编辑客户端私有 MCP 配置文件（例如 `$KIMI_CODE_HOME/mcp.json`），在 `mcpServers` 中追加：

```json
{
  "mcpServers": {
    "tapd": {
      "command": "uvx",
      "args": ["mcp-server-tapd"],
      "env": {
        "TAPD_ACCESS_TOKEN": "<TAPD_ACCESS_TOKEN>",
        "TAPD_API_BASE_URL": "https://api.tapd.cn",
        "TAPD_BASE_URL": "https://www.tapd.cn"
      }
    }
  }
}
```

注意：会话进行中修改 `mcp.json` 不会注入当前会话，**需新开一个会话**后生效；用 `/mcp` 查看连接状态（应显示 `tapd ✓ connected`），也可用 `/mcp-config` 交互式管理。项目级配置文件与用户级同名时项目级优先。

**Claude Code / Cursor / Claude Desktop** — 将同样的 JSON 结构写入各自的客户端私有 MCP 配置文件。

**可选**：需要把消息推送到企业微信群时，在 `env` 里加 `BOT_URL`（企业微信机器人 webhook 地址）。

### 4. 验证安装

```bash
(printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"smoke","version":"0"}}}'; \
 printf '%s\n' '{"jsonrpc":"2.0","method":"notifications/initialized"}'; \
 printf '%s\n' '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'; sleep 15) \
 | TAPD_ACCESS_TOKEN=<TAPD_ACCESS_TOKEN> uvx mcp-server-tapd 2>&1 | head -c 1500
```

能返回 `serverInfo: mcp-tapd` 和工具列表即正常。

## 二、MCP 工具使用（mcp__tapd__*）

常用工具（以 `tools/list` 实际返回为准）：

- `get_user_participant_projects` — 获取用户参与的项目（拿 `workspace_id` 的第一步）
- `get_stories_or_tasks` / `get_story_count` — 需求/任务查询（传 `workspace_id` + `options`）
- `get_bug` / `create_bug` / `update_bug` — 缺陷查询/创建/更新
- `get_workflows_status_map` / `get_workflows_all_transitions` — 查询状态名称和可达流转
- `get_comments` / `create_comments` — 查询和新增评论
- `get_entity_custom_fields` — **查询自定义字段前必须先调用**获取字段配置
- `get_iterations`、`get_timesheets` 等

典型流程（如"查指派给我的 bug"）：

1. 调 `get_user_participant_projects` 获取 `workspace_id`（过滤掉 category 为 organization 的数据）；
2. 调 `get_bug`，`options` 传 `{"current_owner": "<当前用户>", "limit": 30, "fields": "id,title,status,priority,current_owner,created"}`；
3. 返回结果时附上缺陷链接，格式：`https://www.tapd.cn/{workspace_id}/bugtrace/bugs/view/{id}`。

## 三、REST API 兜底（MCP 不可用或未加载时）

- Base URL：`https://api.tapd.cn`
- **认证**：`Authorization: Bearer <TAPD_ACCESS_TOKEN>`（注意：不是 Basic Auth，Basic 会 401）
- 验证凭据：`GET /quickstart/testauth`，返回 `{"status":1,...}` 即有效。
- 常用端点（GET 查询均支持 `limit`/`page` 分页、`fields` 裁剪字段）：

| 操作 | 端点 |
|---|---|
| 需求列表 | `GET /stories?workspace_id=<id>&current_owner=<用户>` |
| 任务列表 | `GET /tasks?workspace_id=<id>` |
| 缺陷列表 | `GET /bugs?workspace_id=<id>&current_owner=<用户>` |
| 迭代列表 | `GET /iterations?workspace_id=<id>` |
| 工时 | `GET /timesheets?workspace_id=<id>` |
| 评论 | `GET /comments?workspace_id=<id>&entry_type=bug&entry_id=<id>` |

完整接口文档：https://open.tapd.cn/document/api-doc/API文档/

MCP 不可用时的写入兜底：先查官方 API 文档确认具体 HTTP method、路径、请求体和返回结构，**不得凭猜测拼接状态或评论写入接口**；写入前核对 `workspace_id`、完整缺陷 ID 和认证结果。每次状态或评论写入后都必须重新读取 `get_bug`/评论接口确认实际结果；响应超时、非明确成功或无法确认是否已写入时，只允许先读回，不得直接重复提交。同一写入动作最多在读回确认“未生效且不存在重复评论”后重试一次。

## 四、缺陷处理工作流（强制）

仅在已确认 TAPD 项目及目标缺陷后执行本流程。状态、负责人、评论等写入须包含在本次明确授权中；仅要求分析或修改本地代码时不自动接收、回填或关闭缺陷。

🔴 **CHECKPOINT · 写入前授权与重开评论门禁**

- 只有在用户明确授权本轮 TAPD 状态、负责人或评论写入后，才允许执行对应写操作；仅要求分析、定位或修改本地代码时，保持 TAPD 不变。
- `重新打开` 缺陷在 `get_bug` 之后只允许先读取评论；评论未完整读取和阅读结论未形成前，**STOP**：不得执行除查询外的写操作、不得改代码、不得准备修复方案。
- 任一强制读取失败、分页未完成、响应不明确或上下文矛盾时，**STOP** 并报告阻塞；不得用猜测补齐缺失信息。
- 本轮代码修复对应 TAPD 缺陷时，创建 Git commit 前必须使用 `get_bug` 返回的完整 19 位缺陷 ID 和 `workspace_id` 校验完整提交信息。commit subject 必须以 `fix(tapd):` 开头并原样包含该 ID；commit body 必须换行写入该缺陷的 TAPD 链接。未获得提交授权时不创建 commit，但一旦创建 commit 就不能省略该 ID 或链接。

🔴 **CHECKPOINT · 修复方案确认**

- `get_bug`、评论、工作流和只读定位/复现可以在方案确认前执行；但在修改业务代码、创建修复提交或为本轮修复写入 TAPD 状态/评论前，必须先向用户给出方案并等待明确认可。
- 方案至少包含：已确认现象与复现证据、已确认/待验证根因、拟修改模块、回归测试、真实环境 E2E 与截图证据、提交信息和 TAPD 回填计划。
- 用户明确说“直接修复”“跳过方案确认”“无需等我确认”等同义指令时，可记录该授权并跳过本检查点；仍不得跳过缺陷读取、重新打开评论门禁、E2E、截图、完整缺陷 ID 提交信息和状态流转规则。
- 仅说“修复这个 bug”“继续处理”或“开始看看”不等于方案认可；未获得认可或明确跳过指令时，**STOP**，只报告方案，不改代码、不创建提交、不写 TAPD。

已授权处理并回填指定 TAPD 缺陷时，按以下顺序执行：

1. **读取缺陷**：工作区已知时跳过项目发现，使用一次 `get_bug` 获取详情、当前状态、标题、负责人、描述和必要字段；工作区未知时才调用 `get_user_participant_projects`。需要查询自定义字段时，先调用 `get_entity_custom_fields`。
2. **规范 ID 与执行重开前置门禁**：以 `get_bug` 返回的完整 19 位缺陷 ID 作为后续评论查询和写入的唯一 ID。若当前状态为 `重新打开`（或工作流返回的等价 reopened 状态），**在任何状态流转、创建评论、修改代码或准备修复前，必须立即使用该完整 ID 调用 `get_comments` 并阅读评论**。评论查询必须按 API 返回的终止标记或总数分页读完；若没有终止标记或总数，则持续读取到空页或返回条数小于请求 `limit`。分页未读完、读取失败或结果不完整时停止，不得继续处理。阅读后必须形成处理依据：上一轮修复/验证结论、重新打开的原因、复现环境或步骤变化、当前需重新核实的边界，并与当前缺陷详情交叉核对；评论为空时也要明确记录“无历史评论”，不能跳过该步骤。非重开状态也要查询评论，以避免重复启动/完成评论。
3. **读取工作流**：完成上述重开门禁（如适用）后，查询状态映射和可达流转，本次处理只读取一次工作流配置；在方案确认前不得流转状态或创建 TAPD 评论。
4. **定位、复现并形成方案**：在修改业务代码前，必须先完成问题定位和可重复复现：记录环境/版本、前置数据、操作步骤、实际结果与期望结果，沿 UI/API/领域/持久化链路定位到责任模块，并保存日志、请求或截图等证据。此阶段只允许只读排查、日志和测试数据准备；无法复现或责任模块不明确时不得编写修复代码，应报告阻塞。基于这些证据形成第五步所需的修复方案。
5. **方案确认门禁**：按“修复方案确认”检查点向用户展示方案并等待明确认可；若用户已明确授权“直接修复”则记录跳过原因后继续。未获认可或跳过授权时保持 TAPD 原状态，禁止修改代码、创建提交、流转状态或写评论。
6. **接收处理并发布启动评论**：方案获认可或明确跳过后，开始本轮修复前必须把缺陷置为 `接受/处理`（当前已是 `接受/处理` 时不重复写；`新`、`重新打开` 等状态须按工作流流转）。状态更新成功后，核对返回状态，再按第五节 HTML 模板发布“初步根因分析”评论；重新打开的缺陷必须把“历史评论阅读结论”纳入该启动评论。若状态流转或启动评论失败，停止后续修复写入；只允许重新读取缺陷和评论确认是否实际生效，确认未生效且无重复后最多重试一次，否则报告阻塞。
7. **排查修复**：基于已复现现象和定位证据确认根因后，实施最小必要修复，并补充能覆盖复现路径的回归测试。若本轮实际创建 Git commit，必须使用以下格式明确标识这是 TAPD 缺陷修复：

   ```text
   fix(tapd): 修复库存扣减异常 [TAPD-<完整19位缺陷ID>]

   TAPD 缺陷：https://www.tapd.cn/<workspace_id>/bugtrace/bugs/view/<完整19位缺陷ID>
   ```

   将示例中的标题、`workspace_id` 和完整 19 位缺陷 ID 替换为本次 `get_bug` 返回的真实值。提交前必须分别用 `git log -1 --format=%s` 和 `git log -1 --format=%B` 核对 subject 与 body：subject 缺少 `fix(tapd):`、完整 ID 或 body 缺少对应 TAPD 链接时，不得进入推送、建 PR 或发布流程。短 ID、仅写标题或仅写 TAPD 链接均不满足要求。多个缺陷应拆分提交；无法拆分时，subject 和 body 必须包含每个完整 ID 及其对应链接。完成代码测试和提交不等于完成 TAPD 状态回填。
8. **E2E 验收门禁**：必须在与缺陷对应的真实 dev/test 业务环境完成端到端验收，覆盖用户触发、接口处理、持久化/展示结果和原回归场景，并留存可复核的环境、版本、步骤和结果证据。只有 E2E 验收明确通过，才允许进入“完成回填”；本地单测、类型检查、构建通过或代码已合并均不能替代该门禁。
8a. **截图证据门禁**：凡涉及 UI、页面展示、用户操作或 E2E 结果的缺陷，必须在复现和修复后分别采集关键截图，至少包含“修复结果”截图；截图证据必须绑定完整缺陷 ID、环境、部署版本/镜像、访问 URL、采集时间、操作步骤和实际结果。截图应保存为稳定的绝对路径，并在最终评论中增加独立的“截图证据”段落；优先引用 TAPD 附件或其他可访问 URL，HTML 使用 `<a href="...">` 或 `<img src="...">`，禁止使用不可访问的 `file://` 链接或只写“见截图”。当前 MCP 仅提供附件读取能力时，不得声称截图已上传 TAPD；只有本地截图而未形成 TAPD 可访问附件/链接时，E2E 证据记为 `partial` 或 `blocked`，不得回填 `已解决`。
9. **完成回填**：E2E 验收通过且截图证据已可复核后，先按第五节 HTML 模板发布“根因、最终修复方案及影响面”评论，明确记录 E2E 证据和截图附件/链接；评论成功后，再将缺陷回填为实际可达的最终状态 `已解决`（或更后状态），并核对返回状态。E2E 未通过、未执行、截图未采集或截图不可访问时，只能补充“待验证”评论并保持 `接受/处理`，禁止改为 `已解决`。

状态值必须以当前工作流实际支持的值为准，不得假设所有项目都使用相同状态。状态更新或评论发布失败时，停止后续写操作并报告失败原因，不得把未完成的处理标记为已完成。

### 快速路径与补录规则

- 缺陷已处于 `接受/处理` 时直接进入排查；处于 `新` 时先查评论再按工作流流转；处于 `重新打开` 时必须先完整读取并阅读评论，提炼上一轮修复、验证结果和本次重开原因，且在确认读取完整前不得流转、写评论或改代码，再按工作流流转为 `接受/处理`。缺陷已处于 `已解决` 或更后状态时，不回退状态；先查完整 ID 对应的评论，缺哪一阶段的固定评论只补哪一条。评论分页终止条件不明确时，按检查点阻塞处理。
- 重新打开的缺陷若评论读取失败、分页未完成、无法确认重开原因，或历史评论与当前缺陷信息矛盾，保持原状态并报告阻塞；不得用猜测替代评论阅读，也不得直接复用上一轮的根因或验证结论。
- 状态进入 `接受/处理` 后，必须先完成定位和复现并通过方案确认门禁（或获得明确的“直接修复”授权）再修改业务代码；只能做只读排查和复现准备，不能以“猜测根因”直接提交修复。
- 同一处理批次已有相同模板评论时不重复创建；写入失败后只能先重查缺陷和评论，确认未生效且没有重复评论后最多重试一次，仍失败则停止并报告，避免重复评论。
- 最终状态按证据选择：仅本地修复和回归通过时保持 `接受/处理`；对应 dev/test 真实环境的 E2E 验收通过后才可填 `已解决`；在产品或测试确认后才填 `已验证`/`已关闭`。三者都必须受当前工作流可达状态约束，不能以提交、PR、CI 或构建结果代替 E2E 验收。

已知 `workspace_id` 和 `bug_id` 时，推荐执行顺序为：

```text
get_bug
→ 获取完整缺陷 ID 和当前状态
→ 若为重新打开：get_comments（使用完整缺陷 ID，分页读完）并形成历史评论阅读结论
→ 查询工作流状态映射/流转规则，并使用已读评论结果避免重复写入
→ 定位责任模块并复现（记录环境、步骤、实际/期望结果和证据）
→ 给出修复方案并等待用户明确认可；若已明确“直接修复”则记录跳过授权
→ 必要时 update_bug：新/重新打开 → 接受/处理
→ create_comments：初步根因分析（重新打开时包含历史评论阅读结论）
→ 基于复现证据确认根因后修复并补回归测试
→ 如创建 Git commit：使用 `fix(tapd):`、完整缺陷 ID 和换行后的 TAPD 链接，并用 git log 核验 subject/body
→ 真实 dev/test 环境 E2E 验收、采集并上传/关联截图证据
→ create_comments：最终根因、方案、E2E验证、截图证据、影响面
→ 仅 E2E 通过后 update_bug：已解决/已验证/已关闭
→ get_bug + get_comments 核验
```

## 五、TAPD 评论 HTML 格式与固定模板

TAPD 评论的 `description` 按 HTML 存储和渲染，裸换行不是可靠的排版契约。传给 `create_comments` 的评论必须使用 `<p>` 划分逻辑段落，在同一字段组内使用 `<br/>` 换行；列表使用 `<ul><li>`。动态内容写入 HTML 前必须转义，避免标题、描述或日志片段破坏评论结构。

- 创建评论后必须用 `get_comments` 回读 `description`，确认固定段落标签仍存在；未回读前不得把评论格式写成已验证。
- 用户明确要求修复已有评论格式时，先读取原评论并确认 MCP 实际提供评论更新工具；仅在原文内容不变的前提下改成 HTML 段落，再回读确认。工具不可用时说明阻塞，不重复新增一条同内容评论。
- 禁止把整段多行纯文本直接包进一个 `<p>...</p>`；HTML 会折叠其中的裸换行，必须让每个预期换行对应 `<br/>`、独立 `<p>` 或 `<li>`。
- 动态字段自身包含换行时，先 HTML 转义，再把每个换行转换为 `<br/>`；不得把原始换行当成排版指令。
- 写入前检查完成评论至少包含标题段、含两个 `<br/>` 的基础信息段和独立的根因、方案、验证、影响面、关联信息、结论段；回读时确认这些结构仍存在，而不是只检查 `<p>` 标签数量。

### 1. 初步根因分析


### 3. 已有评论补充截图证据

适用于缺陷已经有处理/完成评论，但评论缺少截图、截图链接失效，或后续重新完成了真实环境 E2E 的场景。

1. **先核对现状**：重新调用 `get_bug` 获取完整缺陷 ID 和当前状态，再调用 `get_comments` 读取该缺陷的已有评论，并调用 `get_entity_attachments` 检查现有附件。已有可访问且能证明本次结果的截图时不重复补充。
2. **保留历史记录**：除非用户明确要求修正文案，否则不要覆盖或修改原处理评论；补充截图应新增一条独立评论，标题使用 `【截图证据补充】`，并说明它对应哪一次 E2E/复现结果。
3. **准备图片**：截图文件使用稳定的绝对路径保存，文件名包含缺陷短 ID 或完整 ID；截图至少覆盖修复结果，必要时同时保留修复前/复现态。评论必须记录完整缺陷 ID、环境、部署版本/镜像、访问 URL、采集时间、操作步骤和实际结果。
4. **写入图片**：优先使用可访问的 TAPD 附件 URL 或图片 URL，并在 HTML 中使用 `<a href="...">` 或 `<img src="...">`。如果当前 MCP 没有附件上传工具，但 `create_comments` 接受 HTML，可将本地图片转为 `data:image/...;base64,...` 内嵌到评论；这属于“评论内嵌图片”，不得写成“已上传 TAPD 附件”。禁止使用 `file://`、不可访问的本地路径或临时失效链接。
5. **回读校验**：创建补充评论后必须用 `get_comments` 按新评论 ID回读，确认 `description` 同时包含 `<img`、完整缺陷 ID、环境、版本和截图证据段落；只看到评论创建成功或只检查 `<p>` 标签不算验证通过。若图片被清洗、截断或无法访问，补充评论标记为 `partial/blocked`，不得据此回填 `已解决`。
6. **状态处理**：截图只是补齐证据，不改变原有业务结论。已处于 `已解决` 或更后状态的缺陷不回退；截图补充成功后仍需按工作流复核是否需要后续状态。原状态为 `接受/处理` 且截图补充后仍没有完整 E2E 证据时，继续保持 `接受/处理`。

补充截图评论模板：

```html
<p><b>【截图证据补充】</b></p>
<p>缺陷ID：{{bug_id}}<br/>环境：{{环境}}<br/>版本/镜像：{{版本或镜像}}<br/>访问页面：{{URL或页面路径}}<br/>采集时间：{{时间和时区}}<br/>截图文件：{{文件名}}</p>
<p><b>操作步骤：</b>{{触发和验证步骤}}</p>
<p><b>实际结果：</b>{{截图中可核验的结果}}</p>
<p><b>截图：</b></p>
<p><img src="{{可访问图片 URL 或 data:image base64}}" alt="{{bug_id}} 截图证据" /></p>
<p><b>证据状态：</b>{{passed/partial/blocked}}；{{TAPD附件、可访问链接或“评论内嵌图片”}}</p>
```

## 六、操作反例与黑名单

- **禁止先改状态再读重开评论**：`重新打开` 缺陷必须先完成评论分页读取和阅读结论。
- **禁止未获方案认可直接修复**：完成只读定位后，必须等待用户明确认可方案；只有用户明确要求“直接修复”或等价表达时，才可跳过方案确认。
- **禁止把本地结果当作 E2E 结果**：单测、类型检查、构建、提交或 PR 不能单独支持 `已解决`。
- **禁止把本地截图当作 TAPD 截图附件**：评论必须记录截图证据的环境、版本、URL、时间和可访问附件/链接；仅有本地绝对路径时只能标记 `partial/blocked`，不能宣称截图已上传。
- **禁止无截图回填 UI 缺陷**：涉及页面或用户操作的缺陷，缺少修复结果截图、截图不可访问或无法绑定当前完整缺陷 ID 时，不得将 E2E 写成通过或回填 `已解决`。
- **禁止用补充评论覆盖历史结论**：已有处理/完成评论缺截图时，默认新增 `【截图证据补充】` 评论，保留原评论和原状态变更记录。
- **禁止重复补充同一截图**：先查评论和附件；已有同一环境、版本、URL、时间且可访问的截图时，不重复创建评论。
- **禁止在写入响应不明确时直接重试**：先读回缺陷和评论，确认未生效且无重复后才允许最多重试一次。
- **禁止重复创建固定模板评论**：先查同一处理批次已有评论，再决定是否补录。
- **禁止创建不明确标识 TAPD 的修复提交**：对应 TAPD 缺陷的 Git commit subject 必须以 `fix(tapd):` 开头，并包含 `get_bug` 返回的完整 19 位 ID。
- **禁止遗漏 TAPD 缺陷链接**：commit body 必须换行写入 `https://www.tapd.cn/<workspace_id>/bugtrace/bugs/view/<完整缺陷ID>`；提交前必须用 `git log -1 --format=%B` 核验。
- **禁止用短 ID 或标题替代完整 ID**：`12345`、缺陷标题或 TAPD URL 不能替代完整缺陷 ID；多个缺陷必须分别包含完整 ID 和对应链接。
- **禁止泄露凭据**：token 不得进入代码、日志、评论或聊天回显。
- **禁止猜测状态或接口契约**：状态值、流转路径、REST method 和请求体必须以当前项目工作流或官方 API 文档为准。

## 七、注意事项

- 令牌即凭据：**不要**把 token 写进代码仓库、日志或聊天回显；`mcp.json` 属本机私有配置。
- 用户明确要求按上述流程处理指定 bug 时，执行前仍需核对缺陷 ID、工作区、目标状态和评论内容；未明确授权的其他写操作先向用户确认关键字段。
- 查询返回量默认有限制，需要更多数据时分页拉取（`limit` 最大 200）。
- 缺陷/需求状态流转需符合工作流配置，跨状态直接跳转可能报错，先查当前状态再流转。
